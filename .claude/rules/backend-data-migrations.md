# Backend data / migration rules (SQL, schema)

> **Extraction, not new policy.** Every rule below quotes or summarises a
> statement that already exists in [`AGENTS.md`](../../AGENTS.md) (source of
> truth) or in a document `AGENTS.md` links to. Nothing here adds a new coding
> standard. If this file and `AGENTS.md` disagree, `AGENTS.md` wins.

## 1. Schema changes always require human review

> **AGENTS.md:124** — "**Schema changes always require human review** — see
> [`docs/db/MIGRATIONS.md`](../../docs/db/MIGRATIONS.md) for the local-stack
> runbook (pre-flight, two-engineer review, verification queries, forward-only
> warning)."

> **AGENTS.md:180** — "Human review is mandatory for AI-assisted changes. Hard
> rules: no secrets/credentials in code, input validation on all user data, and
> **database migrations plus security-critical code always require human
> supervision**."

- A migration is never an unattended/agent-only change: it needs a human
  reviewer before it is applied.
- `make backend-migrate` is **HUMAN-SUPERVISED** (**AGENTS.md:119**).
- [`docs/db/MIGRATIONS.md`](../../docs/db/MIGRATIONS.md) §6 states the
  two-engineer rule: "Before invoking `make backend-migrate`, paste the planned
  invocation (including the resulting DSN) into the project's engineering
  channel and wait for a thumbs-up from at least one reviewer who is not the
  operator."

## 2. Migrations are forward-only

> **AGENTS.md:124** — the runbook carries the "forward-only warning".

> [`docs/db/MIGRATIONS.md`](../../docs/db/MIGRATIONS.md) §6 — "Migrations are
> forward-only." / "The Nakama migration system used here is **forward-only**.
> There is no automatic rollback: `nakama migrate down` is not used for the
> game migrations."

- Write forward-only migrations; there is no `migrate down` for the game
  migrations, so a shipped migration is never "rolled back" — it is superseded
  by a new forward migration.
- If a migration partially applied, do **not** re-run `migrate up` blindly —
  escalate to the reviewer (`docs/db/MIGRATIONS.md` §6).

## 3. Where migrations live (and where they must not)

> **AGENTS.md:47** — "SQL migrations live only in `backend/data/` — the former
> root `migrations/` partial copy was deleted in issue #1034; never recreate
> it."

> **AGENTS.md:48** — "`backend/data/modules/` is compiled Nakama bundle output
> regenerated by `npm run build:full` — gitignored since issue #996; never
> commit it even though it sits inside the migrations dir."

> **AGENTS.md:12** — "`data/` # Tooling state (flaky-test history, coverage
> history) — NOT SQL migrations".

- New migration files go to `backend/data/*.sql`; the root `migrations/`
  directory must not be recreated.
- `backend/data/modules/` is generated bundle output — never commit it.
- The repo-root `data/` directory holds tooling state, not SQL.

## 4. Verify a migration

> **AGENTS.md:114-121** — "make services-health # confirm stack is healthy
> before touching schema"; "make check-game-schema # pure-read verification
> that game tables exist (issue #891)"; "cd backend && npm run test:schema
> # schema tests".

> **AGENTS.md:153** — "**Schema tests** (`npm run test:schema`) match only
> `tests/integration/schema.test.ts` and need PostgreSQL but not a running
> Nakama server (issue #893) — the cheapest post-migration verification."

- Cheapest post-migration verification: `cd backend && npm run test:schema`.
- Pre-flight the stack with `make services-health`; verify the game tables
  with `make check-game-schema`.
- Key tables: `player_stats`, `catalog`, `inventory`, `loadout`; enums:
  `gear_type` (helm/armor/bow/arrow/amulet), `gear_rarity`
  (common/rare/epic/legendary) — **AGENTS.md:124**; reference:
  `backend/DATABASE_SCHEMA.md`.
