## Summary

On 2026-04-12 a sustained period of elevated end-to-end latency (p95) was observed
across the public API. The incident correlated with elevated database connection
pool utilization and known N+1 query patterns in the match-results path. Mitigation
was achieved via manual scaling and a temporary increase of the connection pool
ceiling. This document captures the timeline, root cause, and follow-up actions
to prevent recurrence.

## Root Cause

The proximate cause was database connection pool exhaustion triggered by traffic
patterns that surfaced pre-existing N+1 query hotspots under concurrent load.
The connection pool was sized for steady-state traffic, not the observed peak,
and no client-side timeout bounded requests from hanging on slow queries.

Contributing factors:

- No defined p95 latency SLO → slow detection and unclear severity classification.
- Load testing had not been run against a 2x peak scenario, so the saturation
  threshold was untested.
- N+1 query hotspots in the match-results read path were known but unaddressed.
- Auto-scale trigger thresholds were not configured, so recovery required manual
  intervention instead of horizontal scaling.

## Lessons Learned

**What went well**

- On-call response time was within SLA.
- Existing dashboards surfaced the latency increase without ad-hoc querying.

**What went poorly**

- No SLO meant severity was judged qualitatively.
- Mitigation required a manual pool ceiling bump; no auto-scale existed.
- Known N+1 hotspots had not been triaged against the load they would generate.

**Where we got lucky**

- Peak traffic was near-but-not-beyond pool exhaustion; a higher spike would
  have caused user-visible errors, not just latency.

**Where we are taking risks**

- Other read paths share the N+1 anti-pattern; this is addressed in scope of A4
  but warrants a broader audit before the next launch window.
